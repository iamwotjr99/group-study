# StudyLink (실시간 온라인 통합 학습 플랫폼)
> **본 저장소는 스터디 '모집/관리'와 '실시간 협업(화상·채팅)'이 파편화된 기존 사용자 경험을 통합하기 위해 개발된 고성능 학습 플랫폼의 백엔드 및 시그널링 서버입니다.** <br>
> 🎓 **동국대학교 컴퓨터공학과 학사 학위 졸업자격 실험보고서 통과 작품 (이재석)**

## 1. 프로젝트 개요
* **프로젝트 한 줄 소개**: DDD 기반의 견고한 스터디 라이프사이클 관리 도메인과 WebRTC P2P Mesh 통신 기반의 실시간 시그널링 엔진을 통합한 통합 학습 플랫폼
* **핵심 문제 정의 (사용자 경험의 파편화)**: 
  기존 스터디 활동은 에브리타임/카페 등에서 '모집'을 한 뒤 디스코드/Zoom 등 '외부 플랫폼'으로 수시 이동해야 하는 번거로움이 존재했습니다. 구루미 같은 기존 화상 플랫폼은 기능은 있으나 역할 부여나 방장 권한 제어 등 체계적인 '그룹 관리' 기능이 부족합니다. 본 프로젝트는 이 경계를 무너뜨려 **모집부터 실시간 화상 스터디까지의 라이프사이클을 단일 플랫폼으로 내재화**했습니다.
* **비기능적 엔지니어링 목표**: DDD 4계층 아키텍처를 통한 도메인 비즈니스 보호, WebRTC P2P 채택을 통한 서버 비용 최소화, 80% 이상의 엄격한 테스트 커버리지 강제 자동화

## 3. 도메인 아키텍처 및 복잡한 요구사항 모델링 (DDD)

### 🏗️ DDD 4-Layered Architecture 사상 기반의 의존성 역전(DIP) 구현
도메인 비즈니스 로직이 외부 기술 인프라(JPA, MySQL 등)의 변경에 요동치지 않도록 Presentation, Application, Domain, Infrastructure 계층으로 책임을 엄격히 격리하고 의존성 역전 원칙(DIP)을 구현했습니다. 

Application 계층은 구체 기술을 알지 못하며 오직 Domain 계층의 인터페이스에만 의존합니다. 영속성 벤더 기술이 전면 교체되더라도 핵심 도메인 코드는 단 한 줄도 수정되지 않는 **개방-폐쇄 원칙(OCP)**을 달성했습니다.

#### [계층별 핵심 역할 및 구성 요소]
*(여기에 도메인 레이어 아키텍처 이미지 배치)*
* **Presentation Layer (표현 계층)**: 사용자의 유저 및 소켓 엔드포인트 요청을 수신하고 응답을 반환하는 책임 전담 (`REST Controller`, `Socket Controller`)
* **Application Layer (응용 계층)**: 비즈니스 흐름 제어, 트랜잭션 경계 설정, 도메인 객체 오케스트레이션 담당 (`Service`)
* **Domain Layer (도메인 계층)**: 외부 기술 프레임워크와 완전히 분리되어 비즈니스 핵심 규칙을 품고 있는 순수한 자바 핵심 코어 계층 (`POJO 도메인 모델`, `Interface Repository`)
* **Infrastructure Layer (인프라 계층)**: 도메인 레이어가 정의한 추상화 리포지토리를 구현하고 구체적인 DB 연동 및 엔티티 매핑 처리 (`JpaRepository 구현체`, `Entity`)

### 📦 트랜잭션 원자성 확보를 위한 3대 애그리게잇(Aggregate) 설계 및 Rationale
단일 트랜잭션 내에서 비즈니스 무결성이 동시 유지되어야 하는 경계를 획정하여 시스템 결합도를 낮추고 응집도를 극대화했습니다.

*(애그리거트 개념도 이미지 배치)*

* **스터디 그룹 애그리게잇 (Aggregate Root: `StudyGroup`)**
  * **책임**: `StudyGroup` 루트가 하위 엔티티인 `Participant`들의 권한 상태 변화와 모집 조건(`capacity`) 무결성을 일괄 제어합니다.
  * **비즈니스 가드 로직**: 방장 권한 승인 시 `studyGroup.approve(hostId, applicantId)` 메서드가 직접 캡슐화된 상태 내에서 현재 승인 멤버 수와 정원을 자가 비교 검증 후 전이를 허용하여 규칙의 무결성을 보장합니다.
* **유저 애그리게잇 (Aggregate Root: `User`)**
  * **분리 사유**: 유저의 회원 탈퇴나 닉네임 변경 등은 스터디 그룹 상태와 무관한 독립적 생명주기를 가집니다. 강한 결합도를 막기 위해 `StudyGroup`은 `User` 객체를 직접 참조하지 않고 **ID를 통한 식별자 참조**를 수행하여 데이터 전파 오염을 원천 차단했습니다.
* **채팅 애그리게잇 (Aggregate Root: `ChatRoom`)**
  * **분리 사유 (성능 최적화)**: 스터디 그룹의 상태 변경은 저빈도 트랜잭션이지만, 채팅 내역 저장은 실시간 고빈도 쓰기(Write) 작업입니다. 동일 애그리게잇으로 묶일 시 발생하는 심각한 **데이터베이스 락(Lock) 병목 현상**을 예방하기 위해 분리 설계하여 독립적인 확장성을 확보했습니다.

### 💎 값 객체(Value Object, VO) 적용을 통한 도메인 자가 검증(Self-Validation)
`Email`, `Password`, `StudyGroupInfo` 클래스는 원시 타입(Primitive Type)을 포장한 순수 값 객체로 설계되었습니다[.
* 생성 시점에 스스로 데이터 포맷 유효성 규칙을 검증하는 **자가 검증(Self-Validation)** 보장.
* 내부에서 `match()`, `encode()` 등 고유 비즈니스 행위를 직접 처리하는 **행위 캡슐화(Encapsulation)**를 만족하여 상위 엔티티의 코드를 간결하게 보호합니다.

## 4. 실시간 통신 및 웹소켓 인가 파이프라인 (Security)

실시간 웹소켓(STOMP) 환경에서 기술적 복잡도를 제어하고 비기능적 보안 요구사항을 충족하기 위해, 웹소켓 연결 시점과 개별 채널 구독 시점의 책임을 명확하게 분리한 **2단계 인증/인가 시스템**을 구축했습니다.

*(실시간 스터디 입장 시퀀스 다이어그램 이미지 배치)*

* **1단계: WebSocket 연결 검증 (인증)**
  * **동작**: 유저가 최초 실시간 스터디 방 진입을 위해 `CONNECT` 요청을 보낼 때 `StompAuthInterceptor`가 헤더의 JWT 토큰 유효성을 검증합니다.
  * **결과**: 검증에 성공하면 해당 사용자 정보 인증 객체를 `SecurityContextHolder`에 저장하여 유효한 연결 세션임을 증명합니다. 만약 유효하지 않은 토큰일 경우 연결을 원천 차단합니다.
* **2단계: 실시간 채널 진입 검증 (도메인 인가)**
  * **동작**: 인증된 세션에서 특정 스터디 방의 실시간 채널을 `SUBSCRIBE`하려 할 때, 인터셉터가 다시 한번 개입하여 요청 경로에서 `roomId`를 추출합니다.
  * **결과**: 추출한 `roomId`와 유저 식별자를 바탕으로 `StudyGroupService.isApprovedMember()`를 호출하여 **"현재 인증된 사용자가 이 스터디 방에 실제 '승인됨(APPROVED)' 상태의 참여자가 맞는지"** 실시간으로 검증하는 도메인 규칙 기반의 인가(Authorization)를 수행합니다. 멤버가 아닐 시 구독이 차단되며 예외가 발생합니다.

## 5. 핵심 기술적 의사결정 및 문제 해결 (Toss Style)

### ⚡ WebRTC 시그널링 레이스 컨디션 해결: Polite Peer 전략을 통한 'Offer 충돌 예외' 원천 방지

* **문제 상황 및 가설 설정**: 미디어 서버가 배제된 WebRTC P2P Mesh 분산 네트워크 특성상, 신규 피어가 입장할 때 두 피어가 동시에 서로를 향해 Offer 패킷을 전송하는 경쟁 상태(Race Condition)가 발생합니다. 이 경우 피어의 로컬 상태 머신이 이미 `have-local-offer`인 상황에서 원격 Offer를 중복 수신하게 되므로, 표준 규격상 `InvalidStateError` 예외가 터지며 미디어 연결이 영구 실패하는 결함을 포착했습니다.
* **논리적 근거 및 해결 알고리즘 설계**: 비동기 소켓 환경에서 전송 타이밍을 통제하는 것은 불가능하므로, 충돌 발생 시 한쪽 피어가 자신의 자원을 즉각 양보하고 롤백하도록 유도하는 충돌 회피(Collision Avoidance) 매커니즘을 설계했습니다. 상호 피어 중 한쪽에 사전에 지정된 `isPolitePeer = true` 역할을 부여하여, 충돌 감지 시 자신이 보낸 Offer를 즉시 롤백 및 폐기하고 상대방의 Offer를 수락하여 Answer를 생성하도록 역할을 강제했습니다.
* **결론 및 성과**: 양보 피어의 즉각적인 롤백 및 `have-remote-offer` 상태 전이가 유기적으로 유도됨을 확인했습니다. 결함 유발 요소였던 `InvalidStateError`를 원천 방지하여, 최악의 비동기 경쟁 트래픽 환경에서도 안정적으로 3인 이상의 P2P 고화질 비디오/스크린 미디어 채널 링크 수립률 100%를 보장했습니다.

### 🧪 엄격한 자동화 테스트 및 신뢰성 제어 (JaCoCo 80% Hard Gate)

* **문제 상황 및 가설 설정**: 스터디 그룹 관리 특성상 방장의 상태 제어, 강퇴, 멤버 자진 탈퇴 등 예외 Edge Case 분기점이 촘촘하게 얽혀 있어 코드 한 줄 수정이 전체 상태 머신의 손상(Side Effect)으로 이어질 위험성이 극도로 높았습니다[cite: 3]. 이에 자동화 테스트 파이프라인 구축과 커버리지 통제를 통해서만 비즈니스 결함을 사전에 완전 필터링할 수 있을 것이라는 가설을 세웠습니다.
* **검증 방식 및 엔지니어링 접근**: RDBMS 목킹에 따른 가짜 쿼리 통과 현상을 방지하기 위해 실제 운영 사양과 동일한 MySQL 인프라 컨테이너 환경인 `Testcontainers`를 기반으로 통합 테스트를 설계했습니다. 이와 동시에 `build.gradle` 스크립트 내에 `JaCoCo` 플러그인을 바인딩하여 전체 테스트 커버리지가 80% 사양을 만족하지 못할 시 빌드 파이프라인 자체가 즉시 실패하도록 엄격히 통제했습니다.
* **결론 및 성과**: 복잡한 권한 및 예외 분기를 방어하는 **총 215개의 계층별 대단위 자동화 테스트 세트를 성공적으로 통과**시켰습니다. 최종 분석 결과 **라인(Code) 커버리지 87%, 분기(Branch) 커버리지 83%** 정량적 통과를 마크하며 소프트웨어의 견고한 비즈니스 무결성을 완벽하게 증명했습니다.

### 📊 CloudWatch 지표 분석을 통한 대용량 미디어 서버 부하 0원 우회 검증

* **문제 상황 및 가설 설정**: 상용 플랫폼이 채택하는 중앙 미디어 가공/분배 서버(SFU/MCU) 방식은 막대한 대역폭 트래픽 비용을 유발합니다. 소규모 도메인 특성에 맞춰 도입한 P2P Mesh 아키텍처가 의도대로 작동한다면, 대용량 비디오 및 화면 공유 스트리밍이 상시 발생해도 서버(AWS EC2) 측의 자원 소모량은 0에 수렴해야 한다는 가설을 수립했습니다.
* **검증 방식 및 엔지니어링 접근**: 3일의 실구동 운영 모니터링 기간 동안 11/09(1명 웹캠 화상 + 2명 고용량 화면 공유 송수신 30분), 11/11(2명 실시간 화면 공유 30분)의 고부하 미디어 트래픽 상황을 의도적으로 발생시킨 후, AWS CloudWatch 인프라 메트릭스를 동적 추적하여 CPU 및 네트워크 입출력 변화율을 정밀 분석했습니다.
* **결론 및 성과**: 실시간 미디어 스트림이 지속되는 구간 내내 AWS EC2의 **네트워크 출력 지표 최댓값은 오직 시그널링 세션 주소 교환에 소모된 507KB에 불과**했습니다[. 이와 동시에 서버 CPU 사용률 지표는 순간 피크치를 통틀어 **최대 9.11% 미만, 평균 5% 미만의 유휴 상태에 가까운 정온 상태를 유지**하여 미디어 트래픽의 100% 피어 간 다이렉트 우회 가설을 정량적으로 완벽 증명했습니다.
